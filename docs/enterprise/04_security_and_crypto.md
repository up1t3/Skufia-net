# ТОМ 4: Безопасность и Криптография (Crypto & Security Low-Level Design)
**Разработчик:** AI SecOps / Crypto Architect | **Статус:** Утверждено | **Алгоритмы:** ECIES, AES-256-GCM, Double Ratchet

Данный документ описывает протокол обмена ключами (End-to-End Encryption), при котором сервер физически не может прочесть контент сообщений. 

---

## 1. Фундаментальный Стек (Client-Side)

Серверу категорически запрещено участвовать в генерации закрытых (Private) ключей. Все криптографические операции происходят строго в `crypto-worker.js` (WebWorker браузера), используя нативный браузерный `window.crypto.subtle`.

*   **Асимметричное шифрование (Key Exchange):** Эллиптическая кривая `Curve25519` (или `P-256` для WebCrypto).
*   **Симметричное шифрование (Message Payload):** `AES-256-GCM` (содержит встроенный тег аутентификации MAC для защиты от подделки).
*   **Хранилище (Key Storage):** Приватные ключи пользователя хранятся локально в браузере в `IndexedDB` с флагом `non-exportable` (если поддерживается браузером).

---

## 2. Алгоритм Первичного обмена (X3DH Key Agreement)

Чтобы Юзер А (Алиса) мог написать Юзеру Б (Бобу), когда Боб находится "Не в сети", используется пред-вычисленная генерация ключей.

### 2.1 Фаза Регистрации (Боб в сети)
При регистрации устройство Боба генерирует:
1.  `Identity Key (IK)` — Постоянный ключ сущности. Публичная часть отправляется на сервер (`public_identity_key`).
2.  `Signed PreKey (SPK)` — Ключ, подписанный IK (подтверждает, что это ключ Боба). Меняется раз в месяц.
3.  `One-Time PreKeys (OPK)` — Пачка из 100 одноразовых ключей. Отправляется на сервер.

### 2.2 Фаза Инициации (Алиса пишет Бобу)
Алиса хочет написать Бобу (который офлайн):
1.  Алиса скачивает (GET) с сервера `IK_bob`, `SPK_bob` и ОДИН ключ `OPK_bob`.
2.  Сервер удаляет выданный `OPK_bob` из своей БД.
3.  Алиса выполняет Elliptic-Curve Diffie-Hellman (ECDH) уравнение между своими приватными ключами и публичными ключами Боба. 
4.  Результат — Вычисление **Master Shared Secret (SS)**. У Алисы и Боба (когда он выйдет в сеть и получит сообщение) теперь есть единый общий симметричный секрет, который сервер не знает.

## 3. Double Ratchet Algorithm (Двойной Храповик)

Если шифровать весь чат одним ключом `SS`, утечка этого ключа приведет к дешифровке всей истории переписки в будущем (нарушение Forward Secrecy).

### 3.1 Метаболизм Ключей (KDF - Key Derivation Function)
*   **KDF Root Chain:** Генерирует новые ключи цепочки.
*   Из `Shared Secret` генерируется `Message Key 1`. Этим ключом шифруется Сообщение 1 ("Привет").
*   Алгоритм `HKDF` (HMAC-based Key Derivation) пропускает ключ через хэш. Появляется `Message Key 2`. Он шифрует Сообщение 2 ("Как дела?").
*   **Уничтожение:** Как только "Привет" отправлено, `Message Key 1` физически уничтожается из памяти устройства (Secure Erase / Dereference). Если ФСБ/Хакеры изымут телефон после отправки "Как дела?", они не смогут расшифровать "Привет", так как математический процесс HKDF является необратимым (нельзя из Key 2 получить Key 1).

### 3.2 Отскок Диффи-Хеллмана (Асимметричный Храповик)
Когда Боб отвечает Алисе, он генерирует **новую** пару асимметричных ключей `Curve25519` и прикрепляет публичный ключ к своему сообщению (Header). Рассчитывается новый `Shared Secret` (Root Key).
Это защищает чат от взлома в БУДУЩЕМ (Post-Compromise Security), так как "ось" ключей полностью проворачивается в новое измерение.

## 4. Шифрование Медиафайлов и Вложений
Передавать 50МБ видео через AES-256-GCM в виде Base64-строки — смерть для оперативной памяти браузера.

### 4.1 Алгоритм Чанкового AES-CTR
1.  Фронтенд локально генерирует случайный симметричный `FileKey` (32 байта) и случайный `IV` (Инициализационный вектор, 16 байт).
2.  Файл читается через `FileReader` чанками по 1МБ. Каждый чанк шифруется в `Service Worker` через алгоритм `AES-CTR` (который позволяет шифровать поточно, без загрузки всего файла в RAM).
3.  Зашифрованный "мусор" грузится частями на Сервер/S3 через Multipart Upload.
4.  Сам текстовый `FileKey` и `IV` добавляются в JSON-структуру сообщения и шифруются текстовым механизмом (Double Ratchet AES-GCM) в поле `encrypted_content`.
5.  В БД сервера файл лежит в зашифрованном виде. Ключ от него лежит в зашифрованном сообщении. Доступ третьих лиц к бакету S3 (Media Attachments) не приведет к утечке фотографий, так как это просто зашифрованные куски байтов.
