# ТОМ 5: UI/UX и Frontend State Machine (Client Architecture Low-Level Design)
**Разработчик:** AI Frontend Lead | **Статус:** Утверждено | **Стек:** Alpine.js, Vanilla CSS, Dexie.js (IndexedDB)

Данный документ описывает жесткие архитектурные паттерны браузерного клиента. Основное правило: браузер является "Тупым View", все тяжелые расчеты вынесены в Web Workers, а источником Истины (Single Source of Truth) является исключительно локальная IndexedDB, а не ответ сервера.

---

## 1. Архитектура Состояния (Offline-First State)

UI не имеет права блокировать ввод (Input) в ожидании ответа сервера.

### 1.1 Optimistic UI Updates
1.  Пользователь нажимает Enter в инпуте.
2.  Объект сообщения с временным ID (например, `"local_abc123"`) и статусом `is_sending: true` **мгновенно** записывается в IndexedDB (через Dexie.js).
3.  Store (Alpine.js) стягивает изменения из IndexedDB и моментально рендерит сообщение на экране.
4.  В фоне HTTP-запрос (или WS) отправляется на сервер под ключОМ идемпотентности (`client_msg_id`).
5.  По получению HTTP 200 OK — статус в IndexedDB меняется на `is_sending: false` (галочка меняет цвет), ID подменяется на серверный PostgreSQL UUID.

### 1.2 Разрешение конфликтов (CRDT / HLC)
Что если два устройства одного юзера были в офлайне (самолет), на обоих удалили сообщение `msg_100` и потом вышли в сеть?
*   На клиенте применяется Hybrid Logical Clock. 
*   **Правило Last-Write-Wins (LWW):** Если время сервера для двух апдейтов совпадет, побеждает устройство с бо́льшим `client_id` (или Worker ID).
*   Конфликты не блокируют UI, так как Worker прокручивает "Catch-up Replay Event Sourcing" — проигрывает все пропущенные события с сервера поверх локальной базы.

## 2. Производительность Рендеринга (Virtual DOM)

Браузер "умирает" при рендеринге > 10,000 DOM-нод. Чат должен поддерживать бесконечный скролл без деградации.

### 2.1 Intersection Observer & Virtual Viewport
1.  **Fixed Height Cache:** При рендере 50 сообщений, высота каждого обсчитывается (через ResizeObserver) и кэшируется в Alpine State.
2.  **Mounting/Unmounting:** Если сообщение ушло за верхнюю границу экрана на +2000px, оно **физически удаляется** из HTML-дерева (`display: none` не работает, так как он всё равно занимает RAM). Вместо него вставляется пустой `div` (Spacer) с закешированной высотой, чтобы скроллбар браузера не прыгал.
3.  **Lottie Паузы:** Векторные анимации (стикеры) жестко стопарятся, если они не видны на экране. Intersection Observer шлет команду `.pause()` в LottiePlayer.

## 3. Матрица Переходов Состояний (FSM - Finite State Machine)

Точные сценарии поведения инпутов и модалок для предотвращения Race-Conditions.

### 3.1 Input State Morphing
*   `State: DEFAULT`: Показывается поле ввода и кнопка "Скрепка" (Медиа) / "Микрофон" (Голосовое).
*   `State: TYPING`: При вводе >= 1 символа "Микрофон" плавно (через CSS transition transform) схлопывается в кнопку "Отправить" (Ароу-сэнд).
*   `State: RECORD_VOICE`: При удержании (TouchStart) "Микрофона" — инпут блокируется overlay-баром "Запись 0:00", включается MediaRecorder API в фоне. TouchEnd отправляет, таун свайп-влево (Swipe to Cancel) обрывает MediaRecorder и удаляет blob.
*   `State: EDITING_MSG`: Хэдер над инпутом выезжает снизу, `message_to_edit_id` записывается в глобальный Store. При нажатии "Отправить", вызывается `PUT /messages` вместо `POST /messages`.

### 3.2 Контекстные Меню (Context Menus)
*   Вызов осуществляется ПКМ (Desktop) или Long-Press 500ms (Мобайл).
*   Меню позиционируется строго через `getBoundingClientRect()` относительно курсора/пальца.
*   **Boundary Check:** Если клик произошел внизу экрана, меню рендерится не вниз, а "выбрасывается" вверх (transform: translateY(-100%)), чтобы не образовался пустой скролл снизу страницы (Layout Break).
