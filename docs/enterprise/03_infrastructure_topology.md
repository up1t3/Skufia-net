# ТОМ 3: Топология Сети и Архитектура Инфраструктуры (Network & Infra Spec)
**Разработчик:** AI DevOps/Infra Architect | **Статус:** Утверждено | **Среда:** K8s / Docker Swarm Ready

Данный документ регламентирует развертывание компонентов вне кодовой базы приложения. Спецификация определяет, как компоненты связываются друг с другом для обеспечения High Availability (Высокой доступности) и отказоустойчивости мессенджера.

## 1. Топология Трафика (Traffic Edge & Load Balancing)

Все запросы из внешнего мира проходят через единый шлюз. Прямой доступ клиентов к Uvicorn/FastAPI запрещен.

### 1.1 SSL Termination & Reverse Proxy (Nginx / HAProxy)
*   **Терминация SSL:** Дешифровка HTTPS/WSS трафика происходит на балансировщике. До FastAPI трафик доходит как обычный HTTP/WS.
*   **WebSockets (WSS -> WS):** Nginx обязан поддерживать долгоживущие соединения. Обязательны директивы:
    ```nginx
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s; # Сокеты не должны обрываться Nginx'ом каждую минуту
    ```
*   **Rate Limiting на уровне Nginx:** Жесткий шейпинг трафика для защиты БД (`limit_req_zone`). Например, не более 5 коннектов в секунду на IP для `/api/v1/auth`.

## 2. Межсерверная Шина Данных (Redis Pub/Sub)

**Проблема:** В High-Load системах поднимается несколько контейнеров бэкенда (`backend-1`, `backend-2`, `backend-3`). WebSocket-соединения — Stateful (содержат состояние). Если Отправитель подключен к `backend-1`, а Получатель к `backend-3`, то `backend-1` не знает сокет Получателя.

### 2.1 Контракт Broadcaster (Шлюз событий)
*   Используется инструмент `broadcaster` (от encode) поверх Redis.
*   Каждый инстанс (воркер) FastAPI подписывается на Redis-канал, соответствующий ID чата (Например: `SUBSCRIBE room_abc123`).
*   Когда Бэкенд 1 сохраняет сообщение в БД, он делает: `await broadcast.publish(channel="room_abc123", message=JSON_PAYLOAD)`.
*   Бэкенд 3, так как он слушает `room_abc123` (потому что туда подключен активный юзер), мгновенно ловит это событие из Redis и пушит его в активный клиентский WebSocket-сокет.

## 3. Очередь Фоновых Задач (Task Queue Broker)

ASGI-сервер (FastAPI) работает в едином Event Loop'е. Запрещено выполнять CPU-bound блокирующие задачи внутри роута (ибо это парализует все остальные WebSocket соединения).

### 3.1 Выделенные Celery / ARQ Воркеры
Задачи выгружаются в брокер (Redis или RabbitMQ). Отдельные процессы `worker.py` забирают их и выполняют.

**Обязательные фоновые задачи (Background Jobs):**
1.  **Генерация BlurHash:** Размытых цветных превьюек для изображений и видео по алгоритму BlurHash.
2.  **Сжатие Медиа:** Генерация H.264 MP4 480p потока из "тяжелых" 4K видео (через `ffmpeg`).
3.  **FCM Push-Уведомления:** Обращение к Google Firebase API может занимать до 2 секунд. Бэкенд должен бросить задачу в очередь и немедленно ответить `200 OK`.
4.  **Сборка Waveform:** Парсинг аудиофайлов (`.ogg`, `.mp3`) и извлечение массива высот (амплитуд) для прорисовки осциллограммы в аудиосообщении.
5.  **Очистка TTL-сообщений:** Сборщик мусора, удаляющий из БД "секретные сообщения", таймер которых вышел. Запускается по cron раз в 5 минут (Celery Beat).

## 4. Инфраструктура Аудио/Видео Звонков (WebRTC Layer)

Звонки между браузерами с использованием WebRTC не работают "из коробки" в 30% сетей (корпоративные фаерволы, симметричный NAT 4G-сетей). Требуются реле-серверы.

### 4.1 STUN/TURN Стек (Coturn)
Разворачивается отдельный контейнер с демоном `coturn`.
*   **STUN (Session Traversal Utilities for NAT):** Дешевая операция. Клиент А спрашивает STUN сервер "Какой у меня реальный публичный IP?". Сервер отвечает. Клиент А отдает этот IP Клиенту Б, и они соединяются напрямую (P2P).
*   **TURN (Traversal Using Relays around NAT):** Дорогая операция (ест трафик сервера). Если STUN не прокатил (NAT слишком строгий), весь медиа-трафик звонка льется через наш сервер (Coturn) и перенаправляется второму клиенту. 
*   **Контракт:** Бэкенд FastAPI генерирует временные `turn_username` / `turn_password` (действуют 24 часа через HMAC), чтобы злоумышленники не использовали наш TURN-сервер для проксирования своего трафика. Эндпоинт: `GET /api/v1/rtc/ice-servers`.

### 4.2 SFU Топология для Групповых Конференций
Для чатов, где более 3 участников.
Запуск выделенного медиа-роутера (например, `mediasoup`). Каждый клиент шлет 1 видеопоток на mediasoup сервер, а mediasoup раздает его остальным 10 участникам звонка, управляя качеством (Simulcast) в зависимости от канала получателя.

## 5. CI/CD и Оркестрация Контейнеров

Инфраструктура строится вокруг автоматизированного пайплайна доставки (CI/CD) на базе GitHub Actions.

### 5.1 Менеджмент окружения (.env)
Отказ от хардкод-кредов (например, PostgreSQL passwords, TURN secrets) в файлах `docker-compose.yml`. Все конфиденциальные данные загружаются в среду выполнения исключительно через защищенный `.env` файл. Схема конфигурации: `.env.example`.

### 5.2 GitHub Container Registry (GHCR)
Сборка Production-образов автоматизирована в `production.yml`. После прохождения тестов образы пушатся в GHCR (`ghcr.io`):
*   `skufia-postgres:latest`
*   `skufia-api:latest`
*   `skufia-celery:latest`
*   `skufia-frontend:latest`
Пуш осуществляется от имени Action-воркера с использованием OIDC/GITHUB_TOKEN авторизации.

### 5.3 Изоляция слоев сборки Nginx
Образ фронтенда содержит `nginx:alpine` с кастомным конфигурационным файлом (`nginx_full.conf`), который инжектится при сборке (`COPY nginx_full.conf /etc/nginx/nginx.conf`) для применения Gzip сжатия и обязательных заголовков безопасности на уровне web-сервера.
